API Gateway — JWT Filter

JwtAuthFilter — AbstractGatewayFilterFactory (Spring Cloud Gateway)

Request arrives
Every inbound HTTP request hits the gateway. Public paths (/auth/register, /auth/login, /oauth2/**) are listed in application.yml as excluded — filter skips them.
Token extraction
Normal requests → Authorization: Bearer <token> header. SSE path (/notifications/my/stream) → ?token=<jwt> query parameter (because EventSource cannot send headers).
HMAC-SHA256 verify
Uses io.jsonwebtoken (jjwt) to parse and verify the JWT signature using the JWT_SECRET env var. On failure → 401 Unauthorized immediately.
Header injection
Extracts subject (userId), email claim, role claim from JWT body. Mutates the request: adds X-User-Id, X-User-Email, X-User-Role headers before forwarding downstream.
Downstream services
Never touch the JWT again. They read @RequestHeader("X-User-Id") Long userId from the trusted gateway-injected header. This is the sidecar identity propagation pattern.

💡 INTERVIEW TALKING POINTS — UML & Design Patterns

  • CQRS justification: "I applied CQRS in job-service and application-service because read and write operations have very different concerns. Reads are cached in Redis and can be eventually consistent. Writes need @Transactional and publish Kafka events. Separating them avoids mixing caching annotations with transactional logic in the same method."
  • Facade pattern in Services: "JobService and ApplicationService are thin facades. They contain zero business logic — they just instantiate the correct command/query object and call the handler. This means the controller is decoupled from handler implementation details."
  • Builder pattern everywhere: "All Entity classes use Lombok @Builder. All Kafka event DTOs use @Builder. This makes test setup clean — you can build a User.builder().email(...).role(...).build() without a 20-argument constructor."
  • Idempotency via unique constraint: "ProcessedKafkaEvent uses a UNIQUE constraint on event_key rather than a distributed lock. The INSERT either succeeds (first time) or throws DataIntegrityViolationException (duplicate), which I catch to skip the duplicate. This is simpler than Redis-based distributed locking."
  • @PrePersist / @PreUpdate lifecycle: "I use JPA lifecycle callbacks instead of service-layer code for setting UUID, createdAt, updatedAt. This means these fields are always set correctly regardless of which code path creates/updates the entity."
  • Denormalization trade-off: "job_title and company_name are stored on JobApplication. This is a deliberate denormalization. The alternative would be a Feign call to job-service every time you list applications — that would add latency and a synchronous dependency. The trade-off is stale data if the job is edited, which is acceptable for a historical application record."
