→
STEP 2

→
STEP 3
Register
POST /auth/register
Role: JOB_SEEKER or RECRUITER
→
STEP 4
Login
POST /auth/login
Returns accessToken + refreshToken
→
STEP 5
Access App
Bearer token in every request

Alternatively: Google OAuth2 via /oauth2/authorization/google → callback → JWT issued

🔔 Notification & Email Flow

User Action
Apply / Status Change / Register / Job Post / Withdraw
→
Kafka Producer
user-events | job-events | application-events topic
→
Notification Service
Idempotency check → parse payload → build message
→
Gmail SMTP
JavaMailSender → HTML email → user inbox
+
SSE Stream
Real-time push to browser via EventSource / SseEmitter
Events and their email actions:
application-events
SUBMITTED → email to applicant + recruiter
STATUS_CHANGED → email to applicant
WITHDRAWN → email to applicant
job-events
CREATED → confirmation to recruiter
DELETED → notify affected applicants
(applicantEmails list in event)
user-events
REGISTERED → welcome email
TOGGLED_STATUS → account notification
DELETED → goodbye email

STEP 2

STEP 3

💡 INTERVIEW TALKING POINTS — User Flows

  • OTP-first registration: "I require email verification before registration — not after. This prevents registering with fake emails and having unverified accounts in the DB."
  • One application per job: "The UNIQUE(user_id, job_id) constraint in job_applications at the DB level prevents duplicate applications even if the API is called simultaneously. The application layer checks first, but the DB is the source of truth."
  • CQRS in job and application service: "Write operations (create job, apply, change status) go through Command handlers. Read operations (search, get by id, list) go through Query handlers. This separates concerns and makes each handler easier to test independently."
  • Recruiter inbox design: "recruiter_id is stored denormalized on every job_application row. This means the inbox query is a single-table SELECT — no JOIN to the jobs table needed."
  • Feedback gating: "The system tracks has_posted_first_job and has_applied_first_job flags on the User entity. After triggering either action, the frontend calls /users/should-prompt-feedback, and if true, shows the feedback modal. This is shown at most once per trigger type."
  • Admin via Feign: "Admin dashboard data comes from 3 services via Feign. If any service is down, Resilience4j falls back to returning 0 for that stat — the dashboard still loads, just with partial data."
